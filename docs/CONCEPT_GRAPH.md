# 개념 그래프 — 옵시디언 노트로 (설계안, 2026-11-21 · 소유자 승인 전)

> **목표(소유자, 2026-11-21).** 토큰을 아끼려면 읽을 양을 줄인다. 인계서는 새 세션이 시작할 때 읽을 양을 줄이고, 개념 그래프는 **사람·옵시디언 노트·개념 지도·코드가 같은 단어를 쓰게 해서** 에이전트가 이것저것 뒤져 읽지 않고 한 번에 찾아가게 한다. 그러면 맥락이 늘지 않고, 새 세션이 온전하게 시작하고, 낡거나 다른 말을 믿는 착각이 줄어든다.
> **소유자 선택(같은 날).** 노트는 **각 저장소 안 폴더**에 둔다(코드와 같은 커밋으로 관리). 폴더 구조는 **코드 폴더 구조를 따라간다**(노트 위치 = 열 파일 위치).
> 이 문서는 `docs/research/ONTOLOGY_DESIGN.md`(10-04 소유자 승인, P1~P4)를 이어받는다. P3(별칭 후보 루프)·P4(조립기)의 재료를 옵시디언 노트 형식으로 바꾸는 것이 이 문서의 몫이다.

## 1. 왜 바꾸나 — 단어가 안 맞아서 못 찾는다

- 개념 후보 매칭(제목 단어가 프롬프트에 들어 있나)은 실사용 로그에서 쓸 수 없었다: 후보가 하나일 때 맞힌 비율 0~1%, 매칭 개선안 9가지 모두 같음(`docs/research/LOOP_PLAN.md` 11-21 절).
- 09-21 V0 측정도 같은 쪽을 가리킨다: 과거 프롬프트 276건에서 개념 지도 어휘 적중 3.3%.
- 원인은 규칙이 아니라 **단어**다. 사람이 일을 부르는 말과 개념 제목이 다르다. 규칙을 고쳐도 소용없었던 이유다. 해법은 개념마다 **사람이 실제로 쓰는 말을 별칭으로** 붙이는 것 — 북극성 2단계("짧은 별칭은 사람이 붙인다")와 같은 방향이고, 아직 입증은 안 됐다.

## 2. 옵시디언 기능이 그래프의 재료가 된다

| 옵시디언 | 개념 그래프에서 | 목표와의 연결 |
|---|---|---|
| 노트 하나 | 개념 하나 | — |
| 노트 머리의 `aliases` | 그 개념을 부르는 여러 말 | **단어 통일** — 프롬프트의 말을 별칭과 맞춘다 |
| `[[링크]]` | 개념 사이 간선(관계 이름을 붙인다) | 이웃은 한 칸만 따라간다 |
| 폴더 경로 | 개념이 사는 코드 위치 | 노트 위치가 곧 열 파일 위치 |
| 이름 바꾸면 링크 자동 갱신·그래프 보기 | 사람이 지도를 고치고 보는 화면 | 사람이 고치기 쉬워야 지도가 낡지 않는다 |

baton은 옵시디언 앱이 없어도 돈다. 노트는 평범한 마크다운이고, 옵시디언은 사람이 보고 고치는 화면일 뿐이다.

## 3. 노트 형식

위치: 저장소 루트의 `concepts/` 아래, **그 개념의 첫 번째 파일이 있는 코드 폴더와 같은 경로**. 예) 파일이 `hooks/handoff-inject.py`이면 `concepts/hooks/인계서 주입.md`. 루트 파일만 걸린 개념은 `concepts/` 바로 아래.

```markdown
---
aliases: [인계서 주입, 이어서, handoff inject]
status: 일치
checked: 2026-11-21
checked_commit: a5f18ca
files: [hooks/handoff-inject.py, lib/rules.py]
docs: [README.md, README.ko.md]
---
# 인계서 주입

- **정해진 것**: …(DECISIONS.md 항목)
- **실제 동작**: …(`hooks/handoff-inject.py:150` 같은 근거)
- **설명된 곳**: …
- **어긋남**: …

## 이웃
- 정본: [[인계서 상한]]
- 전제: [[설정 파일과 우선순위]]
```

- 머리 항목은 지금 `CONCEPTS.md` 메타 줄(상태·확인·파일·문서)을 옮긴 것이다. 본문 네 칸도 그대로다.
- 이웃은 `[[노트 제목]]` + 관계 이름(정본·전제 등, 지금 메타 줄의 `이웃=`과 같은 어휘).
- `concepts/.obsidian/`(사람의 화면 설정)은 `.gitignore`로 뺀다.

## 4. 정본은 하나 — 노트가 정본, `CONCEPTS.md`는 만들어지는 색인

- 옮길 때 한 번: 지금 `CONCEPTS.md` → 노트들(변환 스크립트, 결정론).
- 그 뒤로는 노트가 정본이다. `CONCEPTS.md`는 노트에서 **생성**하는 요약 색인(요약표 + 개념별 메타 줄)으로 두고 "손으로 고치지 않는다"를 맨 위에 적는다. CI가 생성본이 노트와 같은지 본다.
- 이렇게 하면 `fresh.sh`·`check.sh`·`/drift`처럼 `CONCEPTS.md`를 읽는 도구가 그대로 돈다. 도구를 노트 직접 읽기로 바꾸는 것은 그다음.
- 하지 않는 것: 노트와 `CONCEPTS.md`를 둘 다 손으로 고치는 양방향 동기화(정본이 둘이 된다 — 개념 지도가 가장 먼저 잡는 어긋남이다).

## 5. 찾는 법 — 별칭 → 노트 → 이웃 한 칸 → 파일

1. 프롬프트의 말을 노트의 `aliases`·제목과 **낱말 단위로** 맞춘다(조사가 붙은 한국어 포함, 부분 문자열 아님). 사람이 아닌 프롬프트(다른 세션 메시지)는 세지 않는다(`MACHINE`).
2. 프롬프트에 파일·폴더 경로가 있으면 그 경로의 `concepts/` 폴더 노트를 후보에 더한다 — 폴더가 위치를 말해 주는 몫.
3. 맞은 노트 + `[[링크]]` 한 칸 이웃만 모은다. 공유 파일 동시출현 간선은 만들지 않는다(09-21: 개념 9개에 간선 36개로 폭발, 10-04: 커밋 co-change 그래프는 기준선을 못 이겼다).
4. 조립기(P4)가 예산 안에서 노트 본문 대신 **메타·근거 줄**만 싣는다. 실제 동작은 에이전트가 근거 파일을 연다.

별칭은 두 곳에서 온다: 사람이 붙인 것, 그리고 P3 루프(`lib/candidates.py`) — 프롬프트 뒤에 실제로 그 개념의 파일을 연 기록에서 별칭 후보를 뽑고, 결정론 검증 뒤 사람이 승격한다(스펙 21절).

## 6. 합격선 — 재기 전에 고정한다 (소유자 확인 필요)

평가 재료: ① 이력에서 뽑은 사례 모음 20건(`observer/research/cases.json`, 로컬 전용) ② 실사용 로그의 대리 정답(프롬프트 뒤 도구 호출 10번 안에 그 개념 절이 가리키는 파일을 열었나 — 11-21 분석과 같은 정의).

| 비교 | 지금 값 | 제안 합격선 |
|---|---|---|
| 후보가 하나일 때 맞힌 비율(대리 정답) | 제목 매칭 0/112 | **30% 이상** |

## 7. 순서

1. **합치기** — `compiler-shadow` 브랜치에만 있는 그래프 작업(P1 평가·P3 후보 루프·P4 조립기)을 main으로(훅 연결은 #16·신선도 PR 뒤).
2. **노트 형식과 변환** — 3·4절. baton 자기 저장소 지도(개념 12개)로 먼저.
3. **별칭으로 찾기** — 5절, 오프라인 평가로 6절 합격선 판정(비용 0).
