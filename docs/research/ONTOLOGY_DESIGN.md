## 1. 왜 지금 방식으로는 안 되나

- **만드는 비용**: 생성 4.47·갱신 1.42(API 환산, 각 1회), 바쁜 주 흑자·평균 적자 → 판정 보류(`LOOP_PLAN.md` 4단계). LLM이 지도를 쓰는 한 수지는 사용량에 묶인다.
- **맞히는 비율은 모른다**: 개념 주입 -43%는 프롬프트에 제목 단어가 들어가게 골랐을 때다. 실사용 적중은 안 쟀다(`NORTH_STAR.md` 2절). 참고 수치 둘 — V0 도메인 어휘 적중 3.3%(276건 중 9건, 대부분 폴더명·개념 제목 1건 — **다른 매처**, `ROADMAP.md` 2단계), 한 저장소 과거 프롬프트에 지금 제목을 거꾸로 맞춘 19.5%(과대 가능, `LOOP_PLAN.md` 4단계).
- **맥락 정답 라벨이 없다**: `cases.json`(20건)은 정답 **행동**만 채점한다. "필요했던 개념·파일" 필드는 없고, `evidence`(18건에만)는 어긋남 위치이며, 문서에 적힌 `require_read`는 구현돼 있지 않다.
- **이미 실패한 길**: 개념들이 같은 파일을 공유한다는 이유로 개념 간선 → 9개에 36개 폭발. 지도로 오답 교정 → 0/2. 다시 하지 않는다.

## 2. 정답을 어디서 얻나 — 행동이 라벨 (정본 이탈, 밝힘)

09-22 "라벨링 안 함"을 지키면서 recall을 재려면 **세션이 실제로 한 일**을 쓸 수밖에 없다.
- 세션에서 첫 파일을 고친 뒤 **이어서 고친 파일들** = 그 시점에 필요했던 맥락의 하한.
- 세션의 첫 프롬프트 뒤 **고친 파일이 속한 개념** = 그 프롬프트에 맞는 개념.

**이탈**: `NORTH_STAR.md` 3절 선택 4는 행동을 "약한 대리 신호, 보조로만" 두었다. 사례 모음에 맥락 라벨이 없어 Retrieval에 한해 이것을 **주 정답**으로 올린다 — 소유자 판단 대상(6절 2번). 약점: 고쳤다 ≠ 필요한 전부(읽기만 한 것 빠짐), 세션이 틀린 파일을 고쳤을 수 있다. 그래서 **절대값이 아니라 기준선과의 차이**로만 판정한다.

**양과 분할** (10-04 실측):
- 시험 재료: 메인 세션 81개 중 파일 2개 이상 고친 세션 43개(9-02~10-03, 프로젝트 8곳, 최다 12개). 저장소별로는 판정 불가 → **저장소를 합쳐** 세션 단위로 잰다.
- 학습 재료: git 커밋. 9-20 이전 유효 커밋(파일 2~20개)이 저장소별 172·56·40·40·35·18·6·5·3·0개. **유효 커밋 30개 미만 저장소는 사전 제외**(평가 전에 목록 고정).
- **평가 전에 고정할 것(P1의 첫 산출물)**: 세션 ↔ 저장소 대응표(위 세션 수는 프로젝트 폴더 8곳, 커밋 수는 그 기록에서 찾은 git 저장소 10곳 기준이라 아직 1:1이 아니다), 사전 제외 목록, 제외 뒤 남는 시험 세션 수. 이 셋을 기록한 뒤에 E1·E2를 돌린다. 제외 기준의 커밋 수는 9-20 기준 어림이고, 실제 학습량은 세션마다 다르다.
- **고정 결과(10-04, E1·E2 실행 전 기록)** — `graph_eval.py prepare`, 대응표는 `~/.cache/baton/eval/mapping.json`(로컬): 거른 메인 세션 75개 중 지금 git 저장소를 찾은 것 68개(나머지는 작업 폴더가 옮겨져 사라짐 — "못 셌다"). 포함 저장소 7곳(유효 커밋 163·56·54·40·40·40·40, 세션 17·24·3·7·1·1·1), 사전 제외 3곳(유효 커밋 6·3·0, 세션 1·6·7). **E1 시험 후보 세션 22개**(메인 스레드 편집만 셈 — 구현 누락) → **재고정 25개**(서브에이전트 편집 포함, 후보 정의를 E1 계산과 일치, 3-1절). 유효 커밋 40개짜리 넷은 같은 저장소의 사본일 수 있다(세션 각 1개라 결과 영향은 작다).
- **누설 방지 — 세션마다 그 세션 시작 이전 자료만 쓴다**: 그래프는 시작 시각 이전 커밋으로, 별칭은 시작 시각 이전 세션의 프롬프트로, **개념 지도는 시작 시점 커밋의 `CONCEPTS.md`(`git show <커밋>:CONCEPTS.md`)로** 만든다 — 지금의 지도로 과거를 채점하면 그 세션 때문에 나중에 생긴 개념이 정답에 섞인다(19.5%의 "거꾸로 맞추기"와 같은 문제). 그 시점에 지도가 없던 세션은 E2에서 뺀다. 그 세션이 만든 커밋은 시작 뒤라 자동으로 빠진다.

### P2 — 파일 그래프 (스펙 22절, 결정론) + 평가 E1 (비용 0)
- 노드는 **파일**, 간선은 **서로 다른 커밋 3회 이상 함께 바뀜**. 거대 커밋(파일 20개 초과)과 **허브 파일**(`HANDOFF.md`·`DECISIONS.md`·`CONCEPTS.md`·`README.md`·잠금 파일 등 — 목록은 평가 전에 고정)은 뺀다. 노드당 상위 5개 이웃.
- **스펙 22절과의 차이(이탈)**: 스펙은 읽기·수정·테스트·결정 이벤트로 간선을 만든다. 여기서는 학습을 **커밋의 함께 수정**으로만 한다 — 세션 기록이 학습에 쓰기엔 얇고(43개), 읽기 동시출현은 잡음이 크다. 이벤트 간선은 실사용 로그가 쌓인 뒤 다시 본다.
- **금지된 간선과 다른 점**: 금지된 것은 "두 개념이 같은 파일을 공유 → 개념 간선"이다. 파일 층 co-change는 **서로 다른 두 파일이 반복해서 함께 고쳐졌다**는 수정 신호라 다르다. 다만 개념 간선을 개념의 `파일=`로 묶어 파생하면 공유 파일만으로도 이어져 금지된 것을 다시 포함한다 → **개념 간선은 서로 다른 파일 사이의 co-change 간선에서만** 파생하고, **두 개 이상의 개념에 속한 파일은 파생에서 아예 뺀다**(x가 A·B 모두에 속하고 A의 y와 함께 바뀌면 x–y 하나로 A–B가 이어져 공유 파일이 간접적으로 근거가 되기 때문).
- E1: 시험 세션마다 첫 수정 파일을 씨앗으로 이웃 상위 5개를 내고, 그 세션이 **이후 고친 파일**의 recall@5를 잰다.
  - 기준선: (a) 같은 폴더 파일 중 최근 수정순 5개, (b) 저장소 전체 최근 수정순 5개 — 둘 다 같은 "시작 이전" 자료로.
  - **합격선**: 시험 세션 20개 이상(미만이면 "못 셌다"). 부트스트랩(1만 회, 세션 단위·저장소 단위 둘 다)에서 그래프 − 나은 기준선의 recall@5 차이가 **점추정 +10%p 이상이고 95% 구간 하한 > 0**. 개념 층 간선 수 ≤ 개념 수 × 2(지도가 있는 저장소에서). 구간이 0을 걸치면 "판정 불가"로 내고 10-18 이후 두 번째 시험 집합을 기다린다.
  - 실패 시: 그래프와 P3의 "파일 무리" 후보는 멈춘다. P3의 별칭 후보는 그래프를 안 쓰므로 따로 간다.

### P3 — 온톨로지 후보 (스펙 21절: 관찰→후보→검증→승격) + 평가 E2 (비용 0)
- **관찰**(서로 다른 날 3일 이상 — `promote.sh`와 같은 문턱): ① 개념에 안 묶인 채 함께 바뀌는 파일 무리(P2 그래프 필요), ② 기존 개념의 파일을 고치기 직전 프롬프트에 자주 나온 구절 → 그 개념의 **별칭 후보**.
- **후보 저장은 저장소 밖** `~/.cache/baton/candidates/<저장소 해시>.json`. 프롬프트에서 나온 구절이 추적되는 `CONCEPTS.md`에 자동으로 들어가면 10-01 개인 자료 사고와 같은 경로가 된다. **사람이 승격할 때만** `CONCEPTS.md`에 쓴다. 스펙의 "ADD candidate → 자동"은 캐시 안에서만 자동이다(이탈, 밝힘).
- **검증**(결정론): 파일이 지금 존재, 기존 개념·별칭과 중복 아님, `rules.GENERIC_WORDS` 아님, 다른 프롬프트에서 잘못 걸리는 횟수(`setup_scan.triggers`와 같은 방식)가 문턱 이하.
- **승격**: 사람만. MERGE·DELETE·REPARENT도 사람만(스펙 권고). `lib/concepts.py`에 `별칭=` 메타 필드 파싱, driftmap에 "후보 검토" 모드 — ~~둘 다 실사용 2주 뒤, E2 통과 시에만~~ → **10-07 소유자: 측정·E2 판정 전에 만든다**(개념 그래프 완성 기준 = 이 루프, 4절). `별칭=` 파싱은 조립기(`lib/compiler.py` `graph`)에 이미 있다.
- E2: 시험 세션의 첫 프롬프트로 개념을 고르고, 그 세션이 고친 파일이 속한 개념과 대조. 지도가 있는 저장소만, 저장소를 합쳐서.
  - 기준선: 지금의 제목 단어 매처(`rules.concept_hits`) — 같은 시험 세션에서 **먼저 잰다**(실사용 적중의 첫 측정이기도 하다).
  - **합격선**: 별칭 포함 매처의 recall이 기준선보다 **+10%p 이상**(부트스트랩 95% 하한 > 0), precision이 기준선보다 낮지 않음. 시험 세션이 20개 미만이면 "못 셌다".

## 7. P4 그림자 조립기 — 실사용 측정 (10-07 소유자 지시, 데이터 보기 전 사전 등록)

**왜 지금.** 10-07 소유자: "개념 그래프를 실측할 수 있는 수준까지 만든 뒤에 내가 실측해 본다." 같은 날 두 번째 결정: 측정 논의 자체는 그래프 완성(스펙 21절 루프, 4절) 뒤 — 이 절의 방법·합격선은 그때 쓴다. 측정할 물건이 있어야 실사용 측정이 된다. 그림자 모드는 넣을 것을 계산해 판단 로그에만 남기고 **모델이 보는 것은 바꾸지 않는다** — 10-04 결정("동작 변경은 10-18 이후")과 충돌하지 않는다. 실제 주입(`BATON_COMPILER=on`)은 opt-in이고, 기본값을 on으로 바꾸는 것은 아래 판정과 E3 뒤 소유자가 정한다.

**무엇을 고르나** (`lib/compiler.py`, 결정론·비용 0, 프롬프트당 10~40ms 실측):
- 개념 그래프 = `CONCEPTS.md` 메타 줄. 노드=개념, 간선=`이웃`(사람이 적은 전제·정본), 붙은 파일=`파일`, 별칭=`별칭`(사람이 승격한 것만). 커밋 co-change 간선은 쓰지 않는다(3-1·3-2에서 짐). 세 개 이상 개념에 걸린 파일·허브 파일은 개념을 고르는 근거로 쓰지 않는다.
- 씨앗 = 인계서의 작업 파일(백틱 경로 중 실제 있는 것) + 이 세션이 만진 파일(세션 기록 끝 512KB, 서브에이전트 포함).
- 파일 순서(예산 10개): 프롬프트로 맞은 개념의 파일(p) → 인계서 작업 파일(h) → 작업 파일로 맞은 개념의 파일(f) → 이웃 개념의 파일(n) → 씨앗과 같은 폴더 최근 커밋순(d). **이 세션이 이미 만진 파일은 후보에서 뺀다** — 이미 맥락에 있는 파일을 가리키는 것은 아끼는 것이 없다.
- 결정: `DECISIONS.md` 항목(날짜 제목 절·결정 ID 표 행) 중 고른 개념을 "개념 N"으로 가리키거나 그 개념의 파일 이름을 적은 것, 최신 10개. 파일 측정에는 안 들어간다.
- 판정 상태(MATCHED 등)는 **프롬프트로 맞은 개념만** 센다 — 인계서 파일로 붙는 개념은 어느 프롬프트에나 같다.

**로그**(`runs.jsonl`의 `compile`): 고른 개념 번호·종류, 파일 경로(저장소 기준 상대)·출처 코드, 같은 자리에서 계산한 기준선 셋(`folder` 같은 폴더만 · `handoff` 인계서만 · `nograph` 개념 그래프만 뺀 조립기), HEAD, 걸린 시간. 프롬프트 원문은 남기지 않는다.

**정답(라벨링 안 함 — 행동이 라벨, 2절과 같은 약점).** 한 턴 = 사람 프롬프트 하나. 정답 = 그 프롬프트부터 다음 사람 프롬프트 전까지 세션(메인+서브에이전트)이 `Read`·`Edit`·`Write`·`MultiEdit`·`NotebookEdit`로 **이 세션에서 처음** 만진 파일 중, 기록된 HEAD에 이미 있던 파일. 허브 제외. Bash 읽기는 안 센다(3-2와 같은 이유, 과소). 정답이 빈 턴은 recall에서 빼고 수만 따로 보고한다.

**지표와 판정**(`observer/research/compile_eval.py`):
- 턴마다 recall = |고른 것 ∩ 정답| / |정답|, precision = |고른 것 ∩ 정답| / |고른 것|. 같은 턴의 `nograph`·`folder`·`handoff`도 같은 정답으로.
- **주 질문: 개념 그래프가 보태는가** = 조립기 − `nograph`의 recall 차이.
- **합격선**(3절과 같은 숫자): 정답 있는 그림자 턴 30개 이상, 세션 5개 이상(미만이면 "못 셌다"). 세션 단위 부트스트랩(1만 회) 차이의 **점추정 +10%p 이상이고 95% 하한 > 0**, 그리고 조립기 precision이 `nograph`보다 낮지 않음. 구간이 0을 걸치면 "판정 불가", 그 밖(하한 > 0이지만 점추정 +10%p 미만, precision 하락, 구간 전체가 음수)은 "불합격"(10-07 데이터 전 문구 보완 — 코드와 일치시킴).
- 보고만(판정 아님): 출처 코드별 적중 수(어느 재료가 맞혔나), 프롬프트 개념이 있던 턴 중 그 개념 파일(`nograph`에 없던 것)이 정답에 든 비율(**제목 매처의 첫 실사용 적중률**), 조립기 걸린 시간 중앙값·최대, 오류·켬 기록 수, 세션 기록 끝만 읽은 턴 수.
- 비교 범위: 후보도 정답과 같이 **기록된 HEAD에 있던 파일**로만 센다(커밋 안 된 파일은 인계서·개념 후보만 낼 수 있어 한쪽이 기울어진다). 잇기는 같은 문장 프롬프트가 여러 번이면 가장 가까운 시각, 한 프롬프트는 한 기록에만, 슬래시 명령도 턴 경계로 센다.
- 합격하면: E3(실제 주입의 토큰·정답 시험, 3절 P4)로 간다. 불합격이면: 개념 그래프 부분은 그림자로 남기고, `nograph`가 `folder`·`handoff`보다 나은지를 소유자 판단 재료로 낸다. 합격선은 결과를 본 뒤 바꾸지 않는다.
- 알려진 한계(측정 전 기록): 작업 중에 보낸 프롬프트가 큐에 쌓이면 훅은 제출 시점에 돌지만 세션 기록의 사용자 메시지 시각은 꺼내 쓴 시점이다 — 그 사이 만진 파일은 조립기의 빼기 목록에도, 정답에도 없다. 실제 시각 차이는 첫 측정 때 확인한다.
- 측정에 쓰는 것은 `mode=shadow` 턴만이다(`on` 턴은 넣은 것 때문에 행동이 바뀌어 정답이 오염된다).

## 8. P3 승격 루프 — 별칭·새 개념 후보 (10-07 소유자 결정, 데이터 보기 전 고정)

**왜 지금.** 10-07 소유자: 개념 그래프 완성 = 스펙 21절 루프(관찰 → 후보 → 결정론 검증 → 사람 승격). 같은 날 "새 개념 후보" 신호를 소유자가 골랐다 — **구절 + 안 묶인 파일**(선택지 추천안). P3①(커밋 co-change 파일 무리)은 3-1·3-2에서 져 쓰지 않는다. 이 절은 루프를 **만드는 것**이고, 루프가 맥락 찾기를 낫게 하는지(E2)는 측정 논의 때 3절 합격선 그대로 잰다.

**관찰 재료** (`lib/candidates.py`, 결정론·비용 0, 저장소 동작은 안 바꾼다):
- 이 저장소의 Claude Code 세션 기록: 첫 `cwd`가 저장소 안인 세션 + **다른 폴더에서 열었지만 기록에 저장소 경로가 나오는 세션**(리뷰 반영 10-07 — 저장소 밖에서 열고 이 저장소 파일을 고치는 작업 방식이면 전자만으로는 늘 0건). 후자의 다른 일 프롬프트는 오발화 분모에만 들어가 후보를 덜 내는 쪽이다. `--resume`·fork로 다른 기록에 복사된 같은 프롬프트(같은 `uuid`)는 한 번만 센다. `claude -p`·SDK 세션(`entrypoint`가 `sdk`로 시작)은 뺀다(`usage_week`와 같은 규칙). Codex는 안 센다.
- **턴** = 메인 기록의 사람 프롬프트 하나부터 다음 사람 프롬프트 전까지. 사람 프롬프트 판정은 `compile_eval.read_session`과 같다(메타·요약·서브에이전트·`<`로 시작·자동 문구 제외). 슬래시 명령은 턴 경계로만 쓰고 구절은 안 뽑는다.
- **고친 파일** = 그 턴에 메인+서브에이전트가 `Write`·`Edit`·`MultiEdit`·`NotebookEdit`로 고친 저장소 파일(허브 제외). **읽기는 안 센다** — 에이전트가 둘러보며 읽는 파일이 너무 많아 "그 구절이 가리킨 것"의 신호가 흐려진다(설계안 2절의 "고친 것"과 같은 선택).
- **구절** = `rules.phrases`(앞 20단어의 한 단어·두 단어 묶음, 일반어·숫자·한 글자 제외 — `setup_scan`에서 옮김)에서 인계 트리거 말(`rules.TRIGGER`)이 든 것을 뺀 것(뺀 수는 `trigger`로 남김). 두 단어 묶음은 **원문에서 공백 하나로 붙어 있던 것만** — 그래야 승격한 별칭이 부분 문자열 매칭에서 실제로 걸린다(리뷰 반영). **사전 등록된 E2(`graph_eval.py`)는 예전 정의(`phrases_v1`)로 고정했다** — 10-18 재측정이 같은 방법을 쓰게.
- **날** = 그 턴 시각의 로컬 날짜. 문턱은 **서로 다른 날 3일 이상**(`promote.sh`와 같음).

**별칭 후보** — 개념 C의 `파일`을 고친 턴(공유 파일 규칙은 조립기와 같다: 세 개 이상 개념에 걸린 파일·허브는 C의 근거가 아님)의 프롬프트가 **C의 제목·별칭으로는 안 맞았을 때**, 그 프롬프트의 구절을 (구절, C)로 센다.
- 적중 = 그 구절이 든 C 턴 중 **제목·별칭으로 안 맞았던** 턴 수(이미 맞은 턴은 배울 것이 없다), 오발화 = 그 구절이 (대소문자 무시 부분 문자열로) 든 **다른** 사람 프롬프트 수(C 파일을 안 고친 턴 전부 — 조립기가 그 구절로 C를 잘못 고르게 될 횟수).

**새 개념 후보** — 턴에 **안 묶인 파일**(git이 추적함 · 허브 아님 · 어느 개념의 `파일`에도 없음 — 추적 조건은 리뷰 반영, 운영 파일이 후보를 차지하지 않게)이 있고, 그 턴 프롬프트가 어느 개념의 제목·별칭에도 안 맞을 때 그 구절을 센다. 구절마다 그 구절이 든 턴들에서 **2턴 이상 고친 안 묶인 파일**(많은 순 5개)을 그 후보의 파일로, 같은 턴들에서 2턴 이상 파일이 고쳐진 기존 개념을 관련 개념으로 붙인다. 파일이 하나도 안 남는 구절은 버린다. **같은 파일 묶음을 가진 구절들은 후보 하나로 합치고**(관련 개념은 합쳐진 구절들이 든 턴 전부로 다시 센다), 구절은 이름 제안(날 수 많은 순 → 오발화 적은 순 → 적중 많은 순, 3개)으로 남긴다 — 후보의 실체는 파일 묶음이다(스펙 21절 예시의 Observed·Related 모양).
- 적중 = 그 구절이 든 턴 중 후보 파일을 고친 턴 수, 오발화 = 그 구절이 든 다른 사람 프롬프트 수.

**결정론 검증**(둘 다, 통과 못 하면 후보에서 빠지고 사유별 수만 남는다):
1. 서로 다른 날 3일 이상.
2. 일반어·숫자·트리거 말이 아님, 기존 개념의 제목 단어·별칭과 같거나 서로 포함하지 않음.
3. **오발화 ≤ 적중** — 그 구절이 걸리는 프롬프트의 절반 이상이 맞는 턴이어야 한다.
4. 새 개념 후보의 파일은 지금 존재해야 한다.
5. 사람이 이전에 버린 것(`dismissed`)은 다시 안 낸다.
- 순서: 날 수 많은 순 → 오발화 적은 순 → 구절. 상한 별칭 개념당 5개, 새 개념 10개.

**후보 저장**: `~/.cache/baton/candidates/<저장소 실제 경로 sha1 앞 16자>.json`(저장소 밖). 내용: 만든 시각·HEAD·센 세션·턴 수, 단계별 수(0이면 어디서 0이 됐는지), `aliases`·`concepts`, 사유별 탈락 수, `dismissed`. **프롬프트 원문은 남기지 않는다** — 구절만(10-01 사고와 같은 경로라서). 다시 돌리면 `dismissed`만 이어받고 나머지는 새로 쓴다.

**사람 승격** (driftmap 모드 ⑤ 후보 검토):
- 에이전트가 `candidates.py scan`으로 후보를 보이고, 사람이 고른 것만 처리한다. 고르지 않은 것은 그대로 두고, 사람이 "버린다"고 한 것만 `dismiss`.
- 별칭: `candidates.py promote-alias <번호> "<구절>" <저장소 루트>`(인자 셋 정확히 — 쪼개진 구절이 경로로 읽히지 않게) — 그 개념 메타 줄의 `별칭=` 원래 값 뒤에 덧붙인다(없으면 줄 끝에 ` · 별칭=` 추가, `없음`이면 바꿈). 다른 내용은 안 건드린다. 같은 번호 절이 둘이면 거절. 조립기(`compiler.graph`)가 다음 프롬프트부터 그 별칭으로 개념을 고른다.
- 새 개념: 스크립트는 쓰지 않는다. 에이전트가 후보 파일을 실제로 읽고 모드 ③ 절차로 네 면·메타 줄을 채운 초안을 보이고, 사람이 승인하면 쓴다(스펙: ADD 후보는 자동, 지도 반영은 사람).
- `CONCEPTS.md`를 자동으로 쓰는 경로는 없다. MERGE·DELETE·REPARENT 도구는 만들지 않는다(5절).

**완료 조건(테스트로 끝까지)**: 픽스처 세션 기록·저장소에서 별칭 후보가 관찰·검증되고 → `promote-alias`로 `별칭=`이 들어가면 → `compiler.concept_matches`가 그 구절의 프롬프트로 그 개념을 고른다. 새 개념 후보도 픽스처에서 파일 묶음·관련 개념·이름 제안이 나온다. 실제 기록에서는 단계별 수를 보고한다 — 후보 0건은 "못 셌다"(재료 부족)와 "검증에서 다 빠짐"을 구분한다.

**알려진 한계(만들기 전 기록, 리뷰 뒤 보탬)**: 새 개념 후보 id는 파일 묶음의 해시라 문턱을 넘는 파일이 하나 늘면 버린 후보가 다시 나온다. 다른 폴더 세션까지 보려고 세션 기록 전체를 한 번 훑는다(수 GB면 수십 초). `rules.concept_hits`(V0 판단 로그의 제목 매처)는 별칭을 안 본다 — E2의 기준선이라 일부러 그대로 둔다. 구절은 조사를 안 떼고 앞 20단어만 본다(`rules.phrases`의 한계 그대로). 세션 기록 전체를 읽으므로 훅에서는 부르지 않는다(오프라인 명령).

## 4. 순서와 멈춤

- **10-07 순서 변경(소유자, `DECISIONS.md` 10-07 두 번째)**: 실사용 측정 논의(재설치·창 재시작·측정 시작일·7절 판정·10-18 E2 재측정)는 **개념 그래프 완성 뒤**. 완성 = 스펙 21절 루프(관찰 → 후보 → 결정론 검증 → 사람 승격). 그래서 다음 작업은 P3 승격 루프다. 별칭 후보(P3②)는 신호가 정해져 있고, 새 개념 후보는 P3①(co-change 파일 무리)이 멈춰 신호가 비었다가, 같은 날 소유자가 **구절 + 안 묶인 파일**로 정했다(8절). 아래 원래 순서와 합격선은 측정 때 그대로 쓴다.

- **지금(10-04~)**: P1 → E1 → E2. 비용 0, 훅·저장소 동작은 안 바뀐다. 결과는 저장소 이름 없이 별칭(game·app·docsrepo 등)으로만 적는다.
- **10-18 이후**: 실사용 2주 결과 + 두 번째 시험 집합으로 E1·E2 재측정 → 통과한 것만 소유자 승인 받아 P3 승격 도구·P4 shadow.
- 멈춤: 합격선을 못 넘으면 그 단계에서 멈추고 보고. P2 실패는 P2와 P3①만 멈춘다(P3②는 그래프를 안 쓴다). 합격선은 평가 뒤에 바꾸지 않는다.
