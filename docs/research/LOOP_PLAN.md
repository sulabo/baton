# 테스트 루프 계획 — 여러 형태에서 돌리며 고친다 (2026-09-27)

목표는 그대로다: **필요 없는 컨텍스트를 처음부터 만들지 않는다** — 토큰 효율화 + 개념 그래프.
지금까지는 "저장소 둘 × 프롬프트 하나 × 6턴"에서만 쟀다. 여기서는 형태를 바꿔 가며 같은 러너로 돌리고,
루프마다 **바꿀 것 하나 → A/B n=5 → 판정(계속/중단/보류) → 다음**으로 빠르게 넘어간다.

## 먼저 알게 된 것 — 기존 기록 재집계 (추가 비용 0)

이미 돌린 30세션의 `result.usage`를 다시 셌다. [MEASURED] 중앙값, arm당 n=5.
`result.usage`는 세션 누적값이다(게임 off-1에서 메시지별 합 341,164 = result 341,164로 확인).

| 저장소 | arm | 첫 턴 컨텍스트 | 6턴 입력 토큰 합(캐시 포함) | 비용 평균 |
|---|---|---|---|---|
| 문서 저장소 | off | 44,090 | 344,577 | — |
| 문서 저장소 | full | 49,977 | **220,726 (-36%)** | — |
| 게임 | off | 43,987 | 348,967 | 0.50 |
| 게임 | full | 49,416 | **359,095 (+3%)** | 0.44 |

두 가지가 계획을 바꾼다.

1. **재독이 줄어도 토큰은 안 줄 수 있다.** 게임에서 인계서 재독은 5/5→0/5였지만 입력 토큰은 오히려 3% 늘었다.
   주입한 약 5.5K 토큰이 매 턴 컨텍스트에 남기 때문이다(비용은 캐시 읽기가 싸서 12% 낮다).
   → 앞으로 판정은 **재독 수가 아니라 토큰·비용**으로 한다. 재독은 보조 지표.
2. **고정 운영 컨텍스트가 약 44K 토큰이다.** 아무것도 안 넣은 off의 첫 턴이 이미 44K다(Claude Code 시스템 프롬프트 + 전역 지침 + OMC + 스킬 목록).
   인계서(5~6K)보다 8배 크다. 이 중 얼마가 OMC 몫인지는 **아직 분리 못 했다** — 루프 5가 잰다.
   ECC 전환 PRD의 "Context Bloat Ratio"가 바로 이 숫자다.

## 루프 목록 (순서대로)

### 루프 1 — 프롬프트 형태: 주입이 필요 없을 때의 손해

지금 프롬프트는 "핸드오프 읽고 이어서 해줘" 하나라 주입에 유리하다. 실제 세션은 그렇지 않은 요청으로도 시작한다.

- 프롬프트 셋: ① 이어서(현행) ② 인계서와 무관한 작은 작업(저장소마다 하나, 예: 특정 파일 오탈자 찾기) ③ 상태 질문("지금 어디까지 왔어?")
- arm: off / full(SessionStart) / **full-on-demand**(UserPromptSubmit 훅이 프롬프트에 `핸드오프|이어서|인계`가 있을 때만 주입)
- 저장소: 문서 저장소·게임. 규모: 3×3×5×2 = 90세션이면 과하다 → ②③만 새로 돌리고 off/full 두 arm부터(40세션, 약 20달러)
- 판정: ②에서 full의 토큰 증가가 10%를 넘으면 기본값을 on-demand로 바꾼다. SessionStart는 프롬프트를 볼 수 없다는 게 이유.

### 루프 2 — 인계서 형태

- ① **200줄 초과**: 긴 인계서를 200줄에서 잘라 넣는 arm vs 전문. 잘린 뒤쪽을 세션이 다시 여는지, 다음 행동이 잘린 쪽에 있을 때 틀리는지
- ② **낡은 인계서**: 인계서가 코드보다 뒤처진 과거 커밋으로 스냅샷(이력에서 찾는다). 주입하면 에이전트가 낡은 내용을 사실로 믿고 이미 끝난 일을 다시 하는지 — **주입의 위험 쪽**을 재는 유일한 루프
- ③ **분할 구조**(소유자 미결 (c)): 루트 `HANDOFF.md`(위치만) + `handoffs/<업무>.md` 시제품 vs 단일 파일. 결정 근거용

### 루프 3 — 저장소 형태 (일반화)

같은 off/full을 성격이 다른 곳에서. 저장소당 10세션, 약 5달러.

| 저장소 | 왜 |
|---|---|
| app | 코드가 크다(Swift). 인계서 밖 읽기가 클 것 |
| 온톨로지 저장소 | 문서만, 작다. 주입 이득이 거의 없을 곳 — 손해 쪽 확인 |
| baton | 파이썬 + 연구 문서. 인계서 줄당 바이트가 셋 중 가장 크다(110B/줄, 지금 9.6KB) |

### 루프 4 — 개념 그래프: 이력에서 정답을 가져온다

독립 검토 넷이 "진실 신호 없이는 더 시험하지 않는다"고 했고, 라벨링은 하지 않기로 했다(09-22).
대신 **정답이 이미 역사에 남은 사례**를 쓴다. `FINDINGS.md`의 12건은 판정 종류(미구현/낡은 문서/…)가 나중에 코드로 확정됐다.

- 예: 게임 엔딩 판정 — 09-01 커밋으로 스냅샷, 프롬프트 "PLAYER-GUIDE의 엔딩 조건이 맞는지 확인하고 틀렸으면 고쳐줘".
  정답은 **미구현**(문서를 고치면 오답). 이 프로젝트가 시작된 바로 그 사고다
- arm: off / CONCEPTS.md 신선도 요약 주입 / driftmap 스킬 호출
- 지표: 정답 판정 여부(파일 편집 여부로 기계 판정), `DECISIONS.md`·스펙 읽기 바이트, 토큰
- 이게 통과해야 "개념 그래프가 결정 문서 읽기를 줄인다"를 말할 수 있다. 지금은 가설

## 러너 개선 (루프를 빠르게 하려면 먼저)

`observer/research/round2_e_ab.py`에 붙인다. 새 러너를 만들지 않는다.

1. `count`에 **토큰 열**(input·cache_creation·cache_read·output, 첫 턴 컨텍스트) — 위 표를 낸 코드
2. `--prompt` 옵션, `--arms`에 `ondemand`·`trunc200`
3. **예산 가드** `--max-usd` — 누적 비용이 넘으면 멈춤. 한도 결과 제외는 이미 있음
4. 스냅샷 매니페스트 — 원본 커밋·dirty 여부·만든 시각을 스냅샷 안에 기록
5. 루프 4용 정답 판정기 — "금지 파일을 편집했나", "기대 파일을 열었나"

## 가드 (루프 공통)

- 한 세션에서 최대 3라운드. 같은 실패 2회 연속이면 멈추고 보고
- 루프마다 예산 상한을 먼저 정한다(위 추정치 기준). 20세션 넘는 날은 사용량 한도부터 본다
- 원본 저장소는 읽기만. 스냅샷은 `.data/snapshots/`에, 미추적 포함으로 뜬다
- 판정 1쪽 = 숫자 + 실행 명령 + 계속/중단/보류. 서브에이전트는 커밋하지 않는다
