# BATON V0 — 규칙 채점을 셋업에 넣는다

상태: 초안 (코덱스 검토 대기)
관계: `NORTH_STAR.md`(전체 구조)의 첫 구현 단계. 여기 없는 것은 V0가 아니다.

## 한 줄

**프로젝트에 baton을 붙이는 순간, 그 프로젝트의 과거 기록으로 규칙을 시험하고 성적표를 낸다.**
아무것도 바꾸지 않는다. 기다리지도 않는다.

## 왜 이렇게 바뀌었나

처음 V0는 "훅을 달고 2주 관찰해 50건을 모은다"였다. 그런데 이미 기록이 있다.

| 출처 | 작업 문장 (도구 결과·시스템 태그·15자 미만 제외) |
|---|---|
| Claude Code 세션 기록 | 문서 프로젝트 330 · 게임 132 · 앱 56 · 그 외 252 |
| Codex 기록 | 207 |
| git 커밋 메시지 | 449 |

기다려서 50건 모을 이유가 없다. 있는 500건으로 하루 만에 채점한다.
그러면 V0는 별도 단계가 아니라 **`init`이 하는 일**이 된다.

## `baton init`이 하는 일

프로젝트 루트에서 실행한다. 다섯 단계를 순서대로 밟고, 어느 단계든 실패하면 거기까지의 결과를 남기고 멈춘다.

### 1. 규칙 초안

프로젝트에서 도메인 어휘를 뽑아 `.baton/rules.yaml`을 만든다.

| 출처 | 우선순위 | 예 |
|---|---|---|
| `CONCEPTS.md` 개념 이름 | 1 | "엔딩 판정", "팔로워 수" |
| `AGENTS.md` 절 제목 | 2 | "그래프 적립 장치" |
| 최상위 폴더명 | 3 | `src` `specs` `sim-tests` |

개념 지도가 있으면 그 이름들이 곧 그 프로젝트의 도메인이다. 실제로 세 프로젝트가 그렇다.
없으면 폴더명만으로 뼈대를 만들고 **"뼈대"라고 표시한다.** 사람이 다듬는 건 그다음이다.

### 2. 과거 작업 문장 추출

세 곳에서 모은다.

- **Claude Code 세션 기록** `~/.claude/projects/*/*.jsonl`. 폴더 이름은 경로의 한글이 대시로 바뀌어
  역산이 안 된다. 파일 안의 `cwd` 필드가 이 프로젝트 경로와 같은 것만 쓴다.
- **Codex 기록** `~/.codex/history.jsonl`의 `text`. 세션 파일에서 `cwd`를 대조한다.
- **git 커밋 메시지** 첫 줄.

**작업을 시작하는 문장만 고른다.** 대화 중간의 "그래 그럼 이것도"는 앞 맥락 없이는 작업이 아니다.
기준은 둘이다. 세션의 첫 사람 프롬프트, 또는 직전 프롬프트에서 30분 이상 지난 프롬프트.
그 외에 15자 미만과 `<`로 시작하는 시스템 태그를 뺀다.

실측(2026-09-21, 문서 프로젝트): 작업 후보 330건이 이 기준으로 **86건**이 된다. 처음 적었던
150~200은 추정이었고 틀렸다. 작은 프로젝트(앱, 후보 56건)는 같은 비율이면 15건 안팎이라
아래 통과 조건 "프로젝트당 50건"을 못 넘는다. **30분이 너무 엄격한지, 아니면 문턱을 낮출지는
코덱스 검토 항목이다.** 줄어든 쪽이 진짜 작업이라는 원칙은 유지한다.

### 3. 규칙 통과

문장마다 규칙을 돌려 셋을 낸다: 도메인, 작업 종류, 필요 스킬.
각각의 결과는 확률이 아니라 **상태**다.

```
MATCHED     증거가 하나로 모임
AMBIGUOUS   증거가 둘 이상 도메인에 걸림
NO_MATCH    증거 없음
```

증거는 우선순위가 있다. 단독 키워드는 가장 약하고, 두 단어 이상의 구가 강하다.

```
1. 사용자가 명시한 태그
2. 정확한 도메인 구       "refresh token", "엔딩 판정"
3. 두 단어 이상 조합       "token" + "jwt"
4. 단독 키워드            "token"  → 혼자서는 도메인을 정하지 못한다
```

"세션"은 인증 세션일 수도 핸드오프 세션일 수도 있다. 단독으로 걸리면 AMBIGUOUS다.
**AMBIGUOUS를 잘 내는 것이 좋은 규칙이다.** 억지로 하나를 고르지 않는다.

### 4. 성적표

`.baton/calibration.md`에 쓴다.

```
작업 문장 187건 (세션 121 · Codex 40 · 커밋 26)

도메인     MATCHED 61%  AMBIGUOUS 28%  NO_MATCH 11%
작업 종류  MATCHED 74%  AMBIGUOUS 15%  NO_MATCH 11%

AMBIGUOUS 예시 (무작위 5)
  · "세션 정리하고 토큰 효율 개선"        → 인증? 핸드오프? 최적화?
  · ...
NO_MATCH 예시 (무작위 5)
  · ...
```

**MATCHED 비율은 정확도가 아니다.** 맞혔다는 뜻이 아니라 하나로 판단했다는 뜻이다.
정확도는 5단계에서 사람이 답을 붙여야 나온다. 이 구분을 성적표 첫 줄에 적는다.

### 5. 채점 (사람)

`baton label`이 층별 표본을 보여 주고 실제 답을 받는다.

- MATCHED에서 30건, AMBIGUOUS에서 30건, NO_MATCH에서 20건. 합쳐 80건.
- 각 문장에 실제 도메인과 작업 종류를 한 줄로 붙인다.
- 붙이지 않은 것은 "미채점"으로 남기고 분모에서 뺀다.

채점이 끝나면 성적표에 정확도 줄이 추가된다.

```
도메인 정확도  MATCHED 중 맞힘 78%   (30건 채점)
애매함 중 실제 단일 도메인이었던 비율  40%   (30건 채점)
```

두 번째 줄이 핵심이다. **규칙이 "모르겠다"고 한 것 중 사람은 답을 알았던 비율**이
Jev를 넣었을 때 얻을 수 있는 최대치다. 이 숫자가 Jev 도입 여부를 정한다.

## V0에 없는 것

전부 명시적으로 뺀다. 있으면 V0가 아니다.

- 훅. 프롬프트를 가로채지 않는다. 채점이 쓸 만할 때 V1에서 단다.
- 컨텍스트 제거, 스킬 필터, 자동 핸드오프, 에이전트 라우팅.
- Jev. 채점 결과가 필요하다고 말할 때만.
- 그래프·온톨로지 수정. 읽기만 한다.
- 기존 driftmap·baton 스킬 변경. 그대로 돈다.

## 파일

```
.baton/
  rules.yaml         규칙. init이 초안을 만들고 사람이 다듬는다
  tasks.jsonl        추출한 작업 문장. 출처·시각·규칙 결과
  labels.jsonl       사람이 붙인 답
  calibration.md     성적표
```

구현은 파이썬 파일 하나(`observer/baton_init.py`)와 규칙 파일 형식뿐이다.
패키지·Provider 인터페이스·CLI 프레임워크는 V0에 없다.

## 통과 조건

다음 단계(V1, 훅 부착)로 가려면 넷을 넘어야 한다.

| 조건 | 기준 | 못 넘으면 |
|---|---|---|
| 작업 문장 수 | 프로젝트당 50건 이상 | 그 프로젝트는 채점 불가로 표시 |
| 채점 표본 | 80건 중 64건 이상 답 부착 | 정확도 줄을 내지 않는다 |
| 도메인 정확도 | 이 숫자로 판단하지 않는다 | 기준선을 정하려는 것이지 통과 시험이 아니다 |
| AMBIGUOUS 중 실제 단일 | 이 숫자가 Jev 판단 근거 | 20% 미만이면 Jev 불필요로 기록 |

정확도 목표를 미리 정하지 않는다. **처음 재는 것이라 기준선 자체가 산출물이다.**
"60% 아래면 폐기" 같은 문턱은 근거가 없어서 넣지 않는다.

## 코덱스가 세게 볼 자리

1. **작업 시작 문장의 기준.** "세션 첫 프롬프트 또는 30분 공백"이 맞나. 30분은 추정이다.
2. **`init`이 개념 이름을 도메인으로 쓰는 것.** 개념은 "어긋날 수 있는 것"이고 도메인은
   "작업의 영역"이라 같은 층위가 아닐 수 있다. 실제 채점에서 갈리면 3순위로 내린다.
3. **층별 표본 30/30/20.** 통계적 근거가 아니라 손으로 붙일 수 있는 양에서 잡았다.
4. **원티드 기록 포함 여부.** baton을 돌리지 않는 프로젝트의 기록을 규칙 보정에 쓰는 게 맞나.
   사용자가 작업을 말하는 방식의 표본이라 넣었다.
5. ~~Codex 기록의 `cwd` 대조~~ **확인됨.** 세션 파일 127개 전부 `cwd` 필드가 있다.
6. **30분 공백 기준과 "프로젝트당 50건" 문턱이 충돌한다.** 실측으로 드러났다. 셋 중 하나다.
   공백을 늘려 시작 문장을 더 잡거나, 문턱을 30건으로 내리거나, 작은 프로젝트는 채점 대상에서
   빼고 큰 프로젝트에서만 규칙을 보정한다. 저는 세 번째를 권한다. 규칙은 프로젝트마다 다르지
   않고 사용자가 작업을 말하는 방식에 달려 있어서, 큰 곳에서 보정한 규칙이 작은 곳에도 통한다.

## 알려진 함정

- `git log`·`sed`·정규식은 형식이 안 맞아도 오류 없이 0을 낸다.
  **모든 수치는 "센 것 / 못 센 것 / 이유"를 함께 낸다.** 0건은 "없음"이 아니라 "못 셌음"일 수 있다.
- 한글 경로는 정규식에서 자주 빠진다. 경로 매칭에 `[가-힣]`을 넣는다.
- 세션 기록의 `"type":"user"`에는 도구 결과가 섞여 있다. `content`가 문자열이거나
  `text` 블록만 있는 것이 사람 프롬프트다.
