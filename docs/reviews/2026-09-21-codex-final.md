# BATON V0 구현·측정 최종 검토 — Codex

검토일: 2026-09-21  
대상: `코덱스-검토요청.md`, 로컬 저장소 커밋 `9372d5be06f9135e3b65d808e22ea9fe9b702f76`  
범위: 구현과 측정 결과. 스펙 5판은 구현 계약 대조에만 사용했다. 코드·규칙·기존 측정 파일은 수정하지 않았다.

**결론: 65% NO_MATCH는 재현되는 관측이다. 그러나 규칙 방식의 한계나 Jev의 필요성을 검증한 결과는 아니다. 지금은 ③ 여기서 멈춤을 권한다.** 기능 확장은 멈추고, 현재 결과를 보존하고 해석을 제한하는 데서 V0를 닫자는 뜻이다. 측정을 마무리할 의사가 있다면 아래의 작은 라벨 검증까지만 한다. 그 검증 없이 “설계 전제를 검증했다”고 말하는 데에는 **아니오**다.

## 먼저 확인한 사실

요청서의 요약만 읽지 않고, 문서 프로젝트에 남아 있는 `.baton/tasks.jsonl`, `rules.json`, `run.json`, `calibration.md`를 직접 대조했다. 이어 `baton_init.extract()`를 원본 Claude 세션에 실행해 메모리에서만 재추출했다. 기존 산출물을 덮어쓰는 CLI는 실행하지 않았다.

| 확인 대상 | 직접 실행 결과 | 해석 |
|---|---|---|
| 원본 재추출 | user 이벤트 3,038건, accepted 276건. 저장된 tasks와 전체 행 일치 | 현재 보존된 입력에서는 재현됨 |
| 작업 종류 재집계 | MATCHED 68, AMBIGUOUS 29, NO_MATCH 179 | 요청서와 일치 |
| NO_MATCH 비율 | 179 / 276 = 약 64.9% | 반올림한 65%는 맞음 |
| 도메인 evidence 적중 | 9 / 276 = 약 3.3% | 질문 (나)의 **19%와 불일치** |
| evidence 출처별 적중 | 개념 제목 1건, AGENTS 절 제목 0건, 폴더명 9건 | 중복 포함 집계. 개념 적중 1건도 폴더 적중과 겹침 |
| 추가 prefix 필터에 걸린 수 | Base directory 19건, Another Claude session 83건, Request interrupted 8건. 합계 110건 | 386 → 276 차이와 일치. 추가한 5종 중 이번 입력에 잡힌 것은 3종 |
| 지문 대조 | rules `44d2824d89a6`, corpus `1183d3075d31`, score script `fb3cb604265e` | 요청서와 일치 |
| 원본·추출기 대조 | manifest `e3b12bbae0f0`, extractor `ae755aa722b9` | 재추출 지문과 저장된 run.json 일치 |

위 수치는 **직접 실행한 관측값**이다. 라벨 정확도·일반화 성능은 측정하지 않았다. 25% + 11% + 65% = 101%인 것은 정수 반올림 때문이며 집계 오류가 아니다.

질문 (나)의 19%는 출처와 분모를 확인하지 못했다. 현재 run #2의 판단에는 9/276을 쓴다. 또한 “28%가 시스템 문장이었다”보다 **“기존 accepted 386건 중 110건이 추가 prefix 필터로 제외됐다”**가 검증 범위에 정확하다. 접두어 집계의 재현과 110건 각각의 사람/시스템 판정 검증은 다르다.

## (가) 65% NO_MATCH는 발견인가, 착시인가

**현 규칙의 문자 적중 범위에 대한 발견이다. 실제 작업의 65%를 이해하지 못했다는 뜻으로 쓰면 착시다.**

현재 분모는 “검증된 작업”이 아니라 추출기가 받아들인 모든 프롬프트다(`observer/baton_rules.py:74`). 독립 명령뿐 아니라 사실 정정, 동의, 이전 작업의 연속 요청, 맥락이 있어야 이해되는 발화도 들어간다. “핸드오프 읽고 이어서 해줘”는 실제 지시지만 그 문장만으로 기존 일곱 작업 종류 중 하나를 정하기 어렵다. 반대로 “이해하기 쉽게 적어줘”는 문서 작성 지시일 수 있는데 현재 규칙은 question과 documentation을 동시에 낸다.

따라서 원인을 둘로만 나누면 부족하다. **추출 오염, 표현 사전의 부족, 문장만으로 판단하기 어려운 맥락 의존, 분류 체계와 요청의 불일치**를 구분해야 한다. 여러 종류가 정말 동시에 필요한 요청도 있다.

구분하는 최소 방법은 기존 5판의 표본 절차를 끝내는 것이다.

1. **0-A: accepted와 rejected 양쪽을 원문과 대조한다.** 시스템 잔존뿐 아니라 진짜 사용자 문장을 버렸는지도 본다. 사람이 쓴 비작업 발화는 시스템 메시지와 별도로 기록한다.
2. **STEP 2: MATCHED 20 · AMBIGUOUS 20 · NO_MATCH 10을 예측을 숨기고 판정한다.** 기존 SINGLE/MULTI/NONE/UNCLEAR를 유지하고, 원인 메모로 표현 누락·맥락 필요·분류 밖을 남긴다. 제시된 앞부분 예시만 골라 보지 말고 고정 seed로 뽑는다.
3. **NO_MATCH 중 기존 종류로 명확히 답할 수 있는 건과 없는 건을 분리한다.** 전자가 많으면 사전 보완 후보이고, 전후 대화가 있어야 풀리면 맥락 문제가 된다. 시스템·비작업 발화가 많으면 분모 문제가 된다.

이는 초기 오류 탐지용이며 작은 표본으로 모집단 전체를 단정하지 않는다. 전체 비율을 추정하려면 층별 모집단으로 가중해야 한다. 독립 작업 수나 경계 성능까지 말하려면 0-B도 필요하지만, 현재 프롬프트별 문자 적중 분포 자체에 0-B가 필수인 것은 아니다.

지금 쓸 수 있는 결론은 다음 문장이다.

> 현재 v0.1.0의 문자열 규칙은 추출기가 받아들인 276개 프롬프트 중 179개에서 어떤 작업 종류 어휘도 찾지 못했다. 작업 적합성과 추출 정확도는 미검증이다.

**“규칙만으로는 부족하다”라는 방식 전체의 결론은 아직 쓸 수 없다.** “현재 규칙을 자동 라우팅에 충분하다고 인정할 근거가 없다”까지는 말할 수 있다.

## (나) 개념 지도가 라우팅 어휘로 부적합한가

**개념 지도의 효용을 기각할 결과는 아니다. 긴 개념 제목을 그대로 문자열 사전으로 쓰는 방법의 적중이 낮다는 결과다.**

`project_evidence()`는 제목을 거의 그대로 가져오고(`observer/baton_rules.py:40`), `evidence_hits()`는 그 제목 전체가 프롬프트 안에 연속해서 있는지 검사한다(`:66`). 예컨대 저장된 “카테고리 트리의 정체”는 사용자가 “카테고리 트리”라고만 말하면 적중하지 않는다. 개념을 언급하는 것과 개념 제목을 그대로 말하는 것을 같은 사건으로 취급하고 있다.

게다가 9건은 개념 지도만의 수치가 아니다. 폴더명과 AGENTS 제목까지 합친 결과이며, 출처를 분리하니 개념 제목 적중은 1건이다. 현재 domains는 unconfigured여서 **도메인 분류의 정확도나 누락률은 아예 측정하지 않았다.**

후속 실험을 한다면 개념 지도는 정본과 근거 연결용으로 유지하고, 사람이 configure할 때 도메인별로 짧은 별칭·실제 산출물 이름을 연결하는 편이 타당하다. 이는 제안이지 이번 측정으로 입증된 개선책은 아니다. 과거 프롬프트에서 별칭을 뽑으면 본 말뭉치에 맞춘 변경으로 기록하고 새 입력에서 확인해야 한다. 동의어를 잘게 쪼개면 적중이 늘어도 엉뚱한 도메인으로 연결될 수 있으므로 적중률만 최적화하지 않는다.

한국어 폴더명에는 NFC/NFD 표기 차이도 남아 있다. 경로는 NFC로 정규화하지만 폴더명과 프롬프트를 비교하는 함수에는 같은 처리가 없다. 이는 별도의 구현 개선 후보이며, 이번 3.3%의 원인 비중을 측정한 것은 아니다.

## (다) 세 갈래 중 권고와 반증 조건

**권고는 ③ 여기서 멈춤이다. 지금 증거는 ① 사전 확장과 ② Jev 도입 중 어느 쪽의 가치를 뒷받침하는지도 가르지 못한다.** Jev는 문장의 의미를 판단하는 층이다. 이를 넣으면 맥락이 없는 요청도 해결된다는 보장은 없고, 사전을 늘리면 NO_MATCH가 줄어드는 대신 잘못된 MATCHED가 늘 수 있다.

중단은 프로젝트 폐기 판단이 아니다. 이번 V0를 “추출 결함을 발견하고, 현재 규칙의 문자 적중 분포를 확인한 탐색 실행”으로 보존한다. 규칙 개인화와 Jev 구현으로 범위를 넓히지 않는다. 계속 투자할지는 아래 증거가 생길 때 다시 판단한다.

| 지금의 중단 권고를 뒤집을 조건 | 그때의 선택 |
|---|---|
| 원문 대조한 실패 표본에서, 기존 종류로 명확히 분류할 수 있고 단순 표현 누락으로 설명되는 요청이 반복된다. 그 누락이 실제 라우팅에 필요한 일임도 확인된다 | ①을 **별도 후속 실험**으로. 현재 V0 기본 규칙은 보존 |
| 표현 보완 뒤에도 의미·문맥 판별이 필요한 실패가 남고, 동일한 미열람 라벨 집합에서 Rules + Jev가 Rules only보다 잘못된 라우팅을 줄인다. 비용·지연이 사전에 정한 허용 범위 안이다 | ②의 도입 근거가 생김 |
| 실패 대부분이 비작업·맥락 부족 발화이거나, 분류를 개선해도 실제 작업에 도움이 되지 않는다 | ③ 유지 |

수치로 성공 기준을 정한다면 새 평가를 보기 전에 고정해야 한다. 이번 결과를 보고 임의의 합격선을 붙이지 않는다. 비교할 것은 단순 MATCHED 증가가 아니라 **정확한 처리 증가, 잘못된 처리 증가 여부, 판단 보류의 적절성**이다. 같은 276건에서 고친 결과는 `TUNED_ON_SEEN_CORPUS`이며 일반화 검증이 아니다. 이미 본 기록을 뒤늦게 나누는 것만으로 미열람 검증 집합이 되지도 않는다.

## (라) 숫자 해석과 신뢰성을 해치는 구현 문제

아래는 원문 코드를 직접 확인한 사항이다. 현재 68·29·179 집계가 틀렸다는 뜻과, 다음 실행을 믿을 수 있게 보존하지 못한다는 뜻을 구분했다.

### 1. 실행 번호·평가 상태가 실제 변경 이력과 연결되지 않는다 — 우선 수정

`observer/baton_rules.py:87`은 언제나 `run #1`, `:88`은 언제나 `BASELINE`을 출력한다. `:108`은 같은 calibration 파일을 덮어쓴다. `cmd_rules()`도 같은 rules.json을 덮어쓴다(`:54`). `baton_init.py:128`의 추출 역시 같은 tasks.jsonl/run.json 경로를 사용한다.

실제 저장된 성적표는 run #2이지만, 같은 자료를 임시 디렉터리로 복사해 `cmd_score()`를 실행하자 run #1·BASELINE이 나왔다. **저장된 run #2 표제는 현재 채점 코드가 자동 생성하는 결과가 아니다.** 규칙을 조정한 뒤 다시 실행해도 BASELINE으로 남을 수 있다. 5판의 실행 보존·오염 표기 계약이 구현돼 있지 않다.

추출기만 고쳤다고 전역 규칙까지 TUNED로 부를 필요는 없다. 대신 실행 번호, 추출기 변경, 같은 입력을 보고 수정했다는 이력을 분리해서 보존해야 한다. 현재 요청서 끝의 “고치면 run #2”도 이미 run #2인 표제와 맞지 않는다.

### 2. corpus 지문이 내용을 보호하지 못한다 — 우선 수정

`observer/baton_rules.py:86`의 corpus 해시는 accepted 행의 ID만 이어 붙여 계산한다. **본문을 바꾸고 ID를 유지하면 지문이 같다.** 실제 메모리 복사본의 첫 본문을 바꿔 같은 해시가 나오는 것을 확인했다.

원본 manifest 역시 파일 경로와 크기만 해시한다(`observer/baton_init.py:71`). 같은 크기의 내용 변경은 구분할 수 없다. 현재 자료를 직접 재계산해 맞았다는 사실은 유효하지만, 지문만으로 당시 내용을 입증할 수는 없다. 실행별 입력 스냅샷과 내용 기반 해시가 필요하다. 재추출 시 상한도 매번 실행일 다음 날 UTC 0시로 바뀐다(`:70`). 저장된 cutoff를 재실행 인자로 고정하는 경로가 없다.

### 3. 버린 원문이 없어 0-A의 반대편 검증이 막힌다 — 우선 수정

거부한 행은 텍스트나 원본 레코드를 보존하지 않고 바로 추가한다(`observer/baton_init.py:91`). 표본 생성도 이를 복원하지 않으며(`:163`), 라벨 화면에는 “텍스트 없음”만 보인다(`:205`). 저장된 rejected 2,762건 중 `text`가 남은 행은 0건이었다.

따라서 지금 라벨 화면만으로는 **버린 것 중 사람 프롬프트가 얼마나 있었는지** 판단할 수 없다. 원본 행 위치 또는 이벤트 식별자를 남기고 검수 때 원문·블록 구조를 가져오도록 해야 한다. 이미지에 판단 근거가 있으면 이미지도 확인 가능해야 한다.

또한 `is_system()`은 `<`로 시작하는 모든 문장을 버린다(`observer/baton_init.py:20`). 합성 입력 `<button> 버튼을 만들어줘`도 시스템으로 판정됐다. 이런 오탈락은 분포를 바꿀 수 있지만, 이번 자료에서 실제 얼마나 일어났는지는 미검증이다.

### 4. 문자 적중과 의도 분류가 다르다 — 결과 이름과 해석에 반영

`observer/baton_rules.py:60`을 그대로 호출한 합성 사례다. 실제 말뭉치의 오류 빈도를 뜻하지 않는다.

| 입력 | 실제 반환 | 드러나는 문제 |
|---|---|---|
| 왜냐하면 일정이 바뀌었어 | MATCHED / question / 왜 | 설명·배경 진술을 질문으로 셀 수 있음 |
| 이해하기 쉽게 적어줘 | AMBIGUOUS / question, documentation | 하나의 요청도 다중 적중이 됨 |
| README | MATCHED / documentation | 단어 존재만으로 작업으로 판정 |
| readme | NO_MATCH | 전역 규칙은 대소문자에 민감 |
| 핸드오프 읽고 이어서 해줘 | NO_MATCH | 명시적인 이어하기 요청을 기존 어휘가 못 잡음 |

한 프롬프트에 여러 문장, 인용, 부정, 이전 결과 설명이 들어가도 모두 같은 방식으로 센다. AMBIGUOUS가 진짜 복수 작업인 경우도 있으므로 “모호함 = 규칙 실패”가 아니다. 반대로 MATCHED도 정답이 아니다. 문장 분할만으로 인용·부정·맥락 문제까지 해결된다고 보지 않는다.

### 5. 검증과 실패 표시가 아직 일부만 구현돼 있다

- **STEP 2 라벨 경로가 없다.** CLI는 0A·0B만 받는다(`observer/baton_init.py:220`). 표본 추출·라벨·가중 지표를 포함한 V0 전체 검증을 완료한 구현으로 부를 수 없다.
- **domain evidence 추출 실패가 빈 목록처럼 보일 수 있다.** concepts 파서의 종료 코드와 stderr를 확인하지 않는다(`observer/baton_rules.py:38`). 파서 실패와 실제 개념 부재를 구별해야 한다. 이번 35개 제목 추출이 실패했다는 뜻은 아니다.
- **빈 모집단을 처리하지 못한다.** accepted가 0이면 비율 계산에서 0으로 나눈다(`observer/baton_rules.py:84`, `:104`). “측정 불가” 상태를 내는 경로가 필요하다. 이번 276건에는 영향이 없다.
- **보고 예시가 대표 표본은 아니다.** 순회 중 처음 만난 5건의 앞 60자만 보여준다(`observer/baton_rules.py:81`). 뒤에 있는 적중어가 화면에서 잘려 보일 수 있다. 여기서 오염을 발견하는 것은 유용하지만 빈도나 원인의 대표성은 주장할 수 없다.

## 최종 판정

**“이 V0가 설계 전제를 검증했다”: 아니오.**

확인한 성과는 분명하다. 현재 원본으로 추출·분포가 재현되고, 구현 둘의 대조와 예시 확인을 통해 추출 결함을 발견했다. 실제 자료로 검토한 가치가 있다.

다만 V0가 묻던 “현재 BATON 규칙이 실제 작업 표현을 얼마나 설명하는가”에는 아직 문자 적중 분포까지만 답했다. 추출기 판정과 작업 종류의 정답 검증이 없고, 도메인은 미설정이며, 실행 보존 계약도 구현과 어긋난다. **현재 규칙의 낮은 문자 적중은 확인했지만, 규칙 방식의 한계·의미 판단 층의 필요성·라우팅의 실용성은 미검증**이라는 문장으로 이번 검토를 닫는 것이 맞다.
